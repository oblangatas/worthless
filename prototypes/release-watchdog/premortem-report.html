Premortem: release watchdog (WOR-922)

Frame: it is 3 months (~6 releases) from now, and the watchdog failed. 8 investigators ran in parallel, one per failure reason, with read-only access to the repo and the GitHub API. 2026-09-12.

Committed action: pending — your pick below.

Synthesis

Most likely failure

The tests pass against a fake GitHub that behaves differently from the real one (L4 I4). Real --paginate output arrives one page at a time, and the repo has 22,461 runs. Fan-in writes its verdict to a file, not stdout, and exits 1 on a blocked publisher. A naive watchdog then either crashes on every tick or misses the run on page 2.

Most dangerous failure

The issue gets filed and nobody reads it (L3 I5). There is real evidence already: alarm issues #571 (open 17 days, only bot comments) and #603 (open 5 days, 0 comments) were never acted on. A perfect watchdog that writes into a channel nobody reads is still silence.

Hidden assumption

That a GitHub issue reaches you better than the emails you already ignore. The data says it doesn't, yet. The design is sound; the delivery channel is unproven.

Revised plan (what changes in the PR)

  1. Contract test: the run-name format, the create-release job and the "Create the GitHub Release" step are pinned between release-notes.yml and the script, and enrolled in GUARD_MUTATIONS. (drift)
  2. Realistic fake GitHub: it returns multiple pages, with the matching run on page 2. Plus a live read-only test of the query shape, like fan-in's existing one. (api-shape)
  3. Fan-in verdict: read from a temp output file with || true. A blocked publisher files an issue; only a missing verdict counts as a crash. Tested both ways. (api-shape, noise)
  4. Stale approval named: if the pending approval is for an old commit (after a re-tag), the issue says "reject the old run". (approval-detect)
  5. Honest issue text: "never ran (or ran before this watchdog existed)" and "created it by hand? close this". (first-release, drift)

Rejected, with reasons

  • Skip tags whose tree lacks run-name: wrong signal. release-notes.yml runs from main, not from the tag's files.
  • "Re-tag keeps the old date": false. Re-signing creates a new tag object with a new date. v0.3.12's date is its third signing.
  • "Pending run skipped forever": false. The rule checks "waiting" before "in flight", so it alarms after 72h.
  • Exclude rc tags: release-notes.yml deliberately creates prereleases for rc tags, so they are real releases.
  • Tag-push self-health trigger: L2, and it adds a second mode. Measured cron gaps are at most 34h, so a 6h cron still runs at least daily. Documented as a known limit.
  • Separate test file: you asked for guards enrolled in GUARD_MUTATIONS, whose harness only copies test_deploy_static.py. Instead, append at the end to keep rebases small.

Pre-launch checklist

  1. Before merge: triage #571 and #603 (you) — don't add alarms to a channel full of ignored ones.
  2. Fake GitHub paginates, and a test proves a match on page 2 is found.
  3. Deleting the watchdog, the run-name, or the step name each turns a test red (GUARD_MUTATIONS).
  4. After merge: run the workflow manually once and check the log says "ignored" for v0.3.10–12.
  5. First real tag (v0.3.13): confirm the release-notes run title reads Create GitHub Release v0.3.13@<sha>.

Gap check

Not explored: what you do when an issue is correct but inconvenient, such as a known-bad release you chose not to publish. There is no documented "I meant it" path besides closing the issue. That works until the tag moves.
